# 安全配置/密钥管理流程（落地版）

本文档用于将“配置/密钥如何管、如何发版、如何轮换”落地到可执行流程，适用于 `cautod_fastapi` 项目。

---

## 目标与范围

- **目标**：避免敏感信息进入仓库；降低泄露影响面；让配置变更可审计、可回滚、可轮换。
- **范围**：
  - **密钥**：`SECRET_KEY`、OAuth Client Secret、`DIFY_API_KEY`、SMTP 密码、数据库密码、Redis 密码等
  - **非密钥配置**：CORS 允许列表、HSTS/CSP 开关、限流阈值、第三方服务 URL 等

---

## 一、配置分层（必须遵守）

- **代码内**：只允许放“默认值/安全默认策略/非敏感常量”，禁止放任何真实密钥。
- **环境变量**：**唯一可信来源**（生产/测试/开发均应优先用 env）。
- **.env 文件**：
  - `.env.dev` / `.env.prod`：可存在于部署环境，但**不应提交仓库**（若已存在，请确保 `.gitignore` 生效）。
  - `.env.example`：**允许提交**，只提供 key 与示例格式，不放真实值。
- **数据库（可选）**：动态配置（如限流阈值、维护模式）可以在数据库存储，但密钥不建议放 DB；若必须存储，需加密并有访问审计。

---

## 二、密钥命名与归属（建议规范）

- **命名**：全大写 + 下划线，例如 `DIFY_API_KEY`、`MYSQL_PASSWORD`。
- **归属**：
  - **应用密钥**：由后端负责人维护（如 `SECRET_KEY`、JWT 相关）
  - **第三方密钥**：由对应服务 owner 维护（如 OAuth、SMTP、Dify）
  - **基础设施密钥**：由运维/平台维护（如 DB、Redis）

---

## 三、落地流程：新增/修改配置（发版流程）

### 1）变更前检查

- **确认类型**：这是“密钥变更”还是“普通配置变更”？
- **确认影响面**：
  - 是否影响登录/鉴权（如 `SECRET_KEY` 轮换会影响 JWT 校验）
  - 是否影响外部服务调用（如 `DIFY_API_KEY`）
  - 是否影响跨域/浏览器策略（CORS、CSP、HSTS）
- **准备回滚**：旧值保留一段时间（仅限密钥轮换场景），并设定回滚窗口。

### 2）代码侧改动规则

- **允许**：
  - 在 `config.py` 的 `Settings` 中新增字段（非敏感可给默认值，敏感不提供默认值）
  - 在 `core/security_headers.py` / `core/csrf_protection.py` 等处新增“读取配置”的开关
- **禁止**：
  - 把真实密钥写进 `*.py` / `*.md` / `*.json`
  - 在日志中打印密钥/Token/Authorization 完整内容

### 3）CI/发布侧改动（建议）

- **发布前**：
  - 校验必要 env 是否齐全（缺少则拒绝启动）
  - 生产环境强制 `DEBUG_MODE=false`
- **发布时**：
  - 通过安全渠道注入 env（CI secret store / 容器编排 secret / 机器本地 secret）
- **发布后**：
  - 做一次健康检查 + 核心链路回归（登录、任务执行、第三方调用）

---

## 四、密钥轮换（Rotation）流程

### 轮换策略（建议周期）

- **高风险密钥**（外网可触达、权限大）：30~90 天
  - `DIFY_API_KEY`、OAuth Client Secret、SMTP 密码
- **基础设施密钥**：90~180 天
  - DB/Redis 密码（需评估停机/双写方案）
- **应用签名密钥**：90~180 天（视业务可接受程度）
  - `SECRET_KEY`（JWT 签名）

### 轮换步骤（通用）

1. **生成新密钥**（用密码管理器或安全随机生成）
2. **灰度**（若支持双密钥验证则先加新密钥；不支持则安排窗口）
3. **更新部署环境的 secret**（先写入新值）
4. **发布/重启服务**
5. **验证核心功能**
6. **撤销旧密钥**（在回滚窗口结束后）
7. **记录审计**（谁在何时为何轮换、影响范围）

### JWT `SECRET_KEY` 的特别说明

- **风险**：一旦更换，旧 JWT 可能全部失效（用户需要重新登录）。
- **建议**：
  - 若业务需要“平滑轮换”，应实现 **key ring**（允许多个 key 验签、仅用最新 key 签发）。
  - 若允许“强制下线”，可直接更换并通知用户重新登录。

---

## 五、泄露响应（Incident Response）最小流程

当怀疑密钥泄露时：

1. **立即吊销/轮换**（优先轮换外部服务密钥、数据库密码）
2. **收敛访问**（临时限制 CORS、关闭对外入口、提高限流）
3. **排查范围**（日志、CI、镜像、历史提交、聊天工具）
4. **审计与复盘**（补齐：最小权限、secret store、扫描规则、告警）

---

## 六、仓库卫生（必须）

- **新增文件**：提交 `.env.example`（不含真实值）
- **.gitignore**：
  - 必须忽略 `.env*`（除 `.env.example`）
  - 必须忽略 `*.key`、`*.pem`、`*secret*`（按需）
- **扫描**（建议）：
  - pre-commit / CI：secret 扫描（例如 gitleaks/trufflehog）

---

## 七、检查清单（每次发版必过）

- [ ] 没有任何真实密钥进入 PR（代码/文档/配置）
- [ ] 新增/修改的 env key 已加入 `.env.example`
- [ ] 生产环境 `DEBUG_MODE=false`
- [ ] CSP/HSTS/CORS 变更经过验证（Swagger/前端不受影响）
- [ ] 日志中不会打印敏感字段（Authorization、Token、密码、API Key）
