# 执行步骤 Prompt 分解器

## 目标

将用户目标转成一组“可直接发送给 agent 执行”的分步 prompts。  
每一步都要基于当前项目和会话上下文，避免空泛建议。

## 适用场景（触发词）

当用户出现以下意图时启用：

- “帮我拆步骤”
- “给我每一步的 prompt”
- “分阶段执行”
- “做一个 subagent/代理执行清单”
- “按项目现状给执行方案”

## 输入来源（必须优先读取）

在给步骤前，先用现有上下文建立最小事实集：

1. 项目类型与入口（语言、框架、核心目录）
2. 当前任务约束（时间、风险、是否可改代码、是否需要测试）
3. 用户目标与完成标准（Done 的判断）
4. 当前会话线索（已打开文件、最近报错、进行中的改动）

若信息不足，不直接猜测；先补 1-3 个必要澄清问题。

## 产出规则（强约束）

- 每个步骤必须包含：`目的`、`执行 prompt`、`期望输出`、`完成判定`
- 步骤粒度可执行：单步不超过 1 个主要动作
- prompts 使用第二人称祈使句，可直接复制发送
- 对高风险动作（迁移、删除、重构核心）增加“先备份/先验证”步骤
- 默认为“先读后改、先验证后提交”

## 标准流程

1. **确认目标与边界**：把用户话术转成可验收目标
2. **建立上下文基线**：让 agent 先读关键文件/命令输出
3. **拆执行阶段**：按“探索 -> 修改 -> 验证 -> 交付”组织
4. **生成逐步 prompts**：每步一条可发送 prompt
5. **附加回退策略**：失败时给下一条补救 prompt

## 输出模板（必须遵守）

```markdown
# 任务分解：<任务名>

## 前提假设
- <假设 1>
- <假设 2>

## 分步执行 Prompts

### Step 1 - <步骤名>
- 目的：<这一步要解决什么>
- 发送给 agent 的 prompt：
  ```text
  <可直接发送的 prompt>
  ```
- 期望输出：<应返回什么结果>
- 完成判定：<如何判断通过>

### Step 2 - <步骤名>
- 目的：...
- 发送给 agent 的 prompt：
  ```text
  ...
  ```
- 期望输出：...
- 完成判定：...

## 失败分支（可选）
- 若 Step N 失败，发送：
  ```text
  <补救 prompt>
  ```

## 最终交付检查
- [ ] 代码/文档改动与目标一致
- [ ] 验证步骤已执行并记录结果
- [ ] 风险项已说明（若存在）
```

## Prompt 写作规范

- 优先包含具体路径、模块名、命令范围
- 明确“只读探索”或“允许修改”
- 指定输出格式（要点、表格、补丁、测试结果）
- 限制发散：只做当前步骤，不提前做后续步骤

## 快速示例

用户目标：修复鉴权中间件导致的 401 误判，并补测试。

Step 1 prompt（上下文核对）：

```text
先只做只读分析：定位鉴权中间件与路由依赖关系。请阅读相关中间件、依赖注入和受影响路由文件，输出“问题定位摘要 + 受影响接口列表 + 最小修复方案”，暂不修改代码。
```

Step 2 prompt（实施修复）：

```text
根据你刚才给出的最小修复方案，只修改必要文件实现修复。要求：保持现有接口行为兼容，新增或更新注释说明关键判断逻辑，并列出改动文件清单。
```

Step 3 prompt（验证与回归）：

```text
为本次修复补充回归测试并执行相关测试集合，输出测试命令、结果摘要、失败项（如有）及处理说明。若测试无法执行，请给出最小可复现步骤和替代验证方法。
```

## 质量自检清单

- [ ] 是否基于当前项目事实而非通用空话
- [ ] 每一步是否都能单独发送执行
- [ ] 是否提供明确完成判定
- [ ] 是否包含失败分支或回退 prompt
- [ ] 是否覆盖验证与交付步骤

## `/create-subagent` 调用模板（总 prompt）

将下面整段作为一次性 prompt 发送给 `/create-subagent`。  
后续只需要替换“任务描述”。

```text
你是“执行步骤分解子代理”。

请基于当前项目代码库状态与当前会话上下文，把下面任务拆解为可执行步骤，并输出“用户可逐条发送给主 agent 的 prompts”：
【任务描述】
<在这里填写本次任务，例如：修复 security headers 与安全报告不一致问题，并补充回归测试与文档>

请严格遵守以下要求：
1) 先基于现有上下文建立最小事实集；信息不足时先提出 1-3 个必要澄清问题，不要臆测。
2) 输出按“探索 -> 修改 -> 验证 -> 交付”分阶段组织。
3) 每一步必须包含四项：目的、可直接发送的 prompt、期望输出、完成判定。
4) 单步只包含 1 个主要动作，prompt 使用第二人称祈使句，可复制即用。
5) 对高风险操作增加“先备份/先验证”步骤，并提供失败后的补救 prompt。
6) 默认策略是“先读后改、先验证后提交”。
7) 输出语言使用简体中文。

请按以下固定结构输出：

# 任务分解：<任务名>

## 前提假设
- ...

## 分步执行 Prompts
### Step 1 - ...
- 目的：...
- 发送给 agent 的 prompt：
  <text prompt>
- 期望输出：...
- 完成判定：...

### Step 2 - ...
...

## 失败分支（可选）
- 若 Step N 失败，发送：
  <text prompt>

## 最终交付检查
- [ ] 代码/文档改动与目标一致
- [ ] 验证步骤已执行并记录结果
- [ ] 风险项已说明（若存在）
```
